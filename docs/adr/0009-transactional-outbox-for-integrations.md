# Integration messages go through a transactional outbox

A lost ZRA booking report is a compliance incident. Saving a reservation and then dispatching a queue job leaves a crash window that can silently lose the report. Instead, integration recording operations write `outbox_messages` in the **same transaction** as the domain change. After commit, enqueue a drain; a minute sweeper recovers missed dispatches, due retries and expired claims. Outbox messages and their attempt/revision history are the record of truth for delivery, retries, logs and the compliance dashboard. The queue's jobs table is transport only.

## Decision

**One table, one delivery engine** (architecture review, 7–8 October 2026). All integrations share tenant- and property-scoped `outbox_messages`, distinguished by `integration`, rather than `booking_reports`, `fiscal_transactions` and `channel_outbound_messages`. `app/Support/Outbox` owns recording mechanics, claims, ordering, batching, quotas, retries, recovery and the restore gate. Integration domains own jurisdiction rules, subjects, operations, payload builders, transport adapters and delivery policy **declared as data**: batch grouping/maximum size, quota identity/limit, ordered or latest-only mode and its scoped key.

Only integration domains call shared `record`, enforced by an architecture test. Recording requires the caller's existing transaction and subject lock; it never opens an independent transaction. Ordered stream identity is **organization + property + integration + subject type + subject ID**: reservation for ZAN, stay for VFMS. Sequence allocation is serialized under that subject lock. Database uniqueness protects stream-scoped sequences and idempotency keys; subject ULID + sequence alone is not the identity boundary.

## Consequences

- **No HTTP inside a database transaction.** The engine claims work in a short transaction, sends outside it, then persists results with a fenced claim token. One message may be in flight per ordered stream; batching combines independent streams only. Quota data coordinates all workers globally, respects provider retry timings and isolates integrations from each other's backoff.
- **Per-message acceptance, not HTTP success.** Adapter `send(messages)` returns exactly one `accepted`, `rejected`, `retryable` or `unknown` result per input, with provider references and retry timing where available. Only explicit acceptance marks delivery. Confirmed retryable work retries unchanged; expired attempts, timeouts or crashes with uncertain acceptance become unknown. Stale claim holders cannot overwrite later decisions.
- **Unknown is not a retry instruction.** Preserve payload, key and sequence; retry unchanged only under a verified provider idempotency contract, otherwise reconcile first. VFMS `referenceNumber` carries the key, but duplicate behaviour and corrected-payload key reuse remain unverified. A duplicate error alone is never acceptance. ZAN's hotel-code/reservation-number upsert and channel coalescing are not proof that replaying older snapshots is safe.
- **Ordered rejection or exhaustion blocks successors.** Every earlier sequence must be delivered; rejected, exhausted or unknown operations cannot be generically skipped. Authorized correction is available only after confirmed rejection, preserving the original operation. Keep the same key/sequence only when verified provider rules permit corrected-payload key reuse; otherwise remain blocked. Under the subject lock with no active attempt, atomically revise the rejected snapshot, consistently rebuild affected blocked snapshots from their original operations, and audit revisions plus actor/reason. Any rebuilding, validation or audit failure rolls back everything.
- **Latest-only is scoped, not a global bypass.** Integrations define a key scoped by organization, property, integration and the state being replaced. Coalesce only unattempted pending snapshots. In-flight snapshots are immutable; newer successors wait. Unknown delivery holds the key until resolved, while confirmed rejection does not block a newer state. Ordered compliance operations do not inherit this behaviour.
- **Recovery is authorized and audited.** Owners/property managers recover only within their authorized properties; platform compliance operators recover ZAN/VFMS only, not channel-manager work. M1 provides commands, not a UI, requiring explicit actor, property, policy check and reason with an audited outcome. Platform context does not itself authorize recovery. Unresolved messages block property archival through the existing pre-archive extension.
- **Bodies and history are sensitive.** Encrypt payloads, responses and attempt/revision history. Exclude credentials from snapshots, logs and audits. Normal logs/views expose metadata and hashes only; raw reads require a separate policy. M1 has no pruning; an approved production retention policy is required before real guest data.
- **Restore is a delivery and identity problem.** A persistent gate blocks delivery **and integration-producing writes** until both delivery reconciliation and missing identity/history recovery, or a verified safe identity boundary, are complete. PITR can erase identities already seen by providers; the restored maximum sequence is insufficient. VFMS must reconcile delivery; ZAN/channel replay requires a verified safe contract, not an assumption from upsert/coalescing. See [architecture §12](../architecture.md#12-runbook-restore-and-post-restore-reconciliation).

**M1 foundation** ([Spec 2](../spec-2-integration-outbox.md)) includes the shared engine/contracts, scoped recovery commands, archival check, persistent restore gate and fake-contract tests. It excludes real provider clients, lifecycle UI and provider alerts. Fake tests prove foundation behaviour, not provider compatibility, idempotency or restore safety. Real-provider restore/reconciliation contracts belong to **M3**; the complete restore exercise remains the **M4** release gate.
