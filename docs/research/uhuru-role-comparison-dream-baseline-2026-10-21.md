# Dream role comparison baseline

Date: 21 October 2026. Source checkout: `3aff31c`. Issue repository: `Astro-67/the-dream`.

## Evidence boundary

This is a **static Dream source and open-issue baseline**, not a runtime comparison. No browser sessions, user creation, login/access tests, email, issue mutations or credentials are part of this research. The main agent owns Uhuru observations and evidence; no Uhuru result is inferred here. Existing test assertions below were read, not executed.

Scope: four default organization roles, an authorized selected **live property**, ordinary active membership, and no extra direct permissions. Draft/demo onboarding, missing property access, archived properties, customized grants and deployed role synchronization can change observed behavior. `OrganizationRole::permissions()` defines defaults; `ProvisionOrganizationRoles::handle()` synchronizes stored Spatie roles, so source alone does not establish a deployed account's effective grants (`app/Domains/Tenancy/Enums/OrganizationRole.php:46`, `app/Domains/Tenancy/Actions/ProvisionOrganizationRoles.php:18`).

Roles belong to an organization; property memberships constrain where they apply. Owner is eligible for an all-properties grant, not a platform administrator or an automatic cross-organization bypass. `Access::allows()` checks stored permission plus tenant/property membership; `Access::inProperty()` additionally requires a selected property. Reads can use authorized archived history; mutations cannot act in an archived property (`app/Domains/Tenancy/Enums/OrganizationRole.php:35`, `app/Support/Tenancy/Access.php:32`, `app/Support/Tenancy/Access.php:66`; architecture: `docs/architecture.md:128`, ADR `docs/adr/0012-one-tenancy-entry-point-with-platform-as-a-context.md:1`).

## Product decisions, not automatic parity fixes

- **Manager payments/finance:** default Property manager lacks `charges.post` and `finance.view` but already has `reports.view`. Granting payment posting, refunds, corrections or open-balances access would alter approved role semantics, not fix a hidden link. #132/#142 explicitly preserve the existing grants.
- **Guest/identity access:** exposing identity to managers, or guest records to housekeeping, needs an explicit privacy/permission decision. Manager profile access without identity is current tested intent; common-role labels are not permission to remove the independent identity boundary.
- **Housekeeping scope/landing:** distinguish a limited useful landing page from permission to see arrivals/guest/billing payloads. Also distinguish own-assignment completion from the existing property-wide cleaning board; changing ordinary cleaning to assigned-room-only would itself be a product/security model change.
- **Maintenance:** no open maintenance-ticket issue was found; #132 explicitly excludes it. If actual authorized Uhuru evidence later demonstrates a relevant workflow difference, first decide whether Dream should add work orders at all, who may create/assign/close them, and what tenant/property/guest data they expose. Do not equate inventory out-of-service management with a repair-ticket system.
- **Staff/property/rates:** manager editing/removing existing staff, Front desk changing rates/property settings, housekeeping managing unavailability, per-property role assignments, or automatic role combinations all require a decision beyond #142. Preserve grantor/property checks and owner safeguards rather than broadening privileges to match a display label.

No new ticket is justified by this sidecar alone: the overlapping usability gaps are already ticketed, and remaining possible differences need the main agent's real role-session evidence plus a product decision where privileges would change.
